# p11g 方案：按在线通过率重建训练池（下一步最优方案）

**日期**：2026-10-22　**状态**：方案定版，**未实现、未上机**
**上游**：[p11f 训练诊断](p11f-diagnosis.md)（§9 采样档检出 / §9.5 错答直方图）、
[p11f 启动配置](p11d-run-config.md)、[纯 RL 解题能力路线](15-pure-rl-reasoning-plan.md)
**一句话**：把训练池从"宽 band `0.0 1.0` + 半陈旧的探针刻度"改成**按当前策略在线通过率
选出的边界题**，让"每生成一组都带正确性对比"从 36% 提到 ~92%。**一个变量：训练池组成。**

---

## 1. 为什么是这一步（全部来自 p11f 实测）

| 读数 | 值 | 含义 |
|---|---:|---|
| 采样档 acc 增益 | +2.35pp，z **p=0.003** | RL 首次被检出有效（贪心档测不出） |
| 其中交卷率通道 | **74%** | 条件精度只 +0.7pp |
| dev-like 池 **inert 组占比** | **64.3%** | 全对 57.4% + 全错 6.9%，`task_adv_guard` 全部丢弃 |
| 错答质量在 p≤5/8 | **82%** | 模型"有时做得出"的题 |
| 错答质量在 p=0 且**零梯度** | **27.5%** | 全错组被丢弃 ⇒ 训练完全看不到 |

**推论**：当前最贵的不是"样本不够"，而是**每三次生成里有两次不产生任何正确性梯度**。
而它的来源是可知的——`--difficulty_band 0.0 1.0` 只排除**表值**恰好等于 0 或 1 的行，
而宽带 850 行里近一半（探针值 0.875 + 1.0）是"接近掌握"的题，它们在 `n=8` 下
大量产出全对组（惰性组的主体）。

**算术（用 p11d §1.1 的探针直方图，仅作量级示意）**：

| band | 池子行数 | `n=8` 组里"有对有错"的期望占比 |
|---|---:|---:|
| `0.0 1.0`（现状） | 850 | ~36% |
| **`0.1 0.8`** | **499** | **~92%** |

即：**砍掉 41% 的题（都是近乎做对的题），把惰性组从 64% 压到 ~9%。**
被砍的题在评测上本来就基本答对，训练它们只是占算力。

## 2. 目标与判据（写死，防事后解释）

### 2.1 主判据：采样档（贪心档无功效，见 §9.2）

| 指标 | 判据 | 不接受 |
|---|---|---|
| **Average@8 acc** | 相对 **p11f step400** Δ ≥ **+2pp** 且配对均值 z **p<0.05** | 贪心档 Δacc；跨档比较 |
| **acc / fmt / 条件精度** | 三者**联合**报告；条件精度不得退 **>1.5pp** | 只看 acc；用 acc 不显著反判条件精度为噪声 |
| 批次 | p11g 与 p11f 的 step400 **同一命令同一批**（同 `gpu_mem`、同执行预算、同 seed） | 复用历史文件跨批比 |

### 2.2 过程判据（本轮的直接靶）

| 指标 | 期望 | 数据源 |
|---|---:|---|
| **`M_raw`（可评分混合组占比）** | **≥ 80%**（p11f 实测 62%） | 生成端日志 + `rlab.sigstats` |
| `difficulty_filter.json` 的 `kept` | 明显小于 850，且 `p_one`/`band_out` 有读数 | `out_dir/difficulty_filter.json`（已落盘） |
| `[sw]` 零权重样本 | **= 0** | 训练日志（每 10 步一行） |
| 符号翻转 | **= 0** | `sigstats` |
| token/update | 不高于 p11f | `sigstats` |

### 2.3 三条"立即停"

1. `difficulty_filter.json` 的 `kept` 与 p11f 几乎相同 ⇒ 表没换成功（指纹 strict 本应拦住，
   若没拦则是更大的问题），**停**。
2. `M_raw < 70%` ⇒ 池子组成没生效，**停**，先查表与 band，不要接着跑完。
3. 条件精度退 >1.5pp 且 acc 退 >2pp ⇒ 池子过窄（丢了必要的题），**停**。

## 3. 方案（一个变量：训练池组成）

### 3.1 主池：边界题 = 在线通过率严格落在 `(0.1, 0.8)`

- **刻度来源换成当前策略的在线率**（`rlab.passrate` 从 p11f 自己的 `record.jsonl` 聚合），
  而不是 2026-10 的 `k=8` 探针值。探针值有两个毛病：协议档可能已变、精度低。
- **band 收成 `0.1 0.8`**，理由：`n=8` 下"有对有错"的概率
  $1-p^8-(1-p)^8$ 在 p∈[0.15,0.8] 才 ≥70%。band 语义是**开区间**
  （`rate >= hi → 排除`、`rate <= lo → 排除`，见 [data.filter_qas_by_difficulty](<rlab/data.py#L511-L532>)）。
- **只信最近窗口**：`passrate` 吃整份 record、是**跨权重版本的生命周期平均**，
  早期弱策略会拉低刻度。做法是先用 `tail` 造一份最近窗口的 record 副本再聚合
  （见 §4.1 的两张表对照）。

### 3.2 明确不在主池里的两类题（以及它们的去向）

| 桶 | 判据 | 主池 | 去向 |
|---|---|---|---|
| **easy / 近掌握** | 在线率 ≥ 0.8 | ❌ | 本轮直接舍弃（评测上本来就答对）。防遗忘由 KL(β=0.04) 承担；若 §2.1 主判据通过但 held-out 显示遗忘，下一轮再加 15% 配额 |
| **hard / 全错** | 在线率 ≤ 0.1 | ❌ | 现在在主池里也**必然零梯度**（全错组被丢）⇒ 舍它不损失任何现有梯度。它是 **27.5% 错答质量**的来源，靠**阶段 2 的独立探索通道**回收 |
| **boundary** | 0.1 < 在线率 < 0.8 | ✅ | 全部 |

> 注意 band 的 `lo`：`lo=0.0` 时只排除恰好 0；用 `lo=0.1` 是为了把"罕见可解"
> （k=19 下 1/19=0.053）也请出主池 —— 它们在 `n=8` 下仍有 34~43% 的概率整组全错，
> 属于阶段 2 的探索对象，而不是主池的正常供给。

### 3.3 阶段 2（本轮不做）：hard 桶的绿色通道

doc15 阶段 D 的最小版：对 hard 桶用 **固定 16 次新 seed** 采样

- 只要出现 ≥1 次正确 → 用新刻度把它升进 boundary，**下一轮以当前策略重新生成常规组**
  （**绝不把离线探索轨迹当 on-policy 组上传** —— 那是 off-policy 污染）；
- 仍全错 → 保留在 hard，下次探索再试（**不永久判死**）；
- 预算上限：探索开销计入总生成 token，控制在 **~10%** 以内（doc15 §阶段C 的要求）。

**为什么放到阶段 2**：它需要两处**新增代码**（§7），而阶段 1 的价值（惰性组 64%→~9%）
不需要任何新代码。先拿到阶段 1 的读数，再决定要不要为 27.5% 的错答质量付这笔工程费。

## 4. 执行步骤

### 4.0 前置（~1 小时，单臂贪心）：修复后的 no-box/C 画像

`e166120` 修掉了"废调用末段负优势被覆盖成 0"，但**还没在任何口径下重测过**。
它不动权重，只动梯度路径，所以**要用重训后的 ckpt 才看得出效果**——本轮只把它当作
下一轮的既成条件，先确认修复没有把 C 桶推向更坏：

```bash
# 训练已在跑就跳过；这一步只是"修复后基线"取证
python -m rlab.eval --algo retool_math --skip_base \
  --models fixed_s400=./rlab_new/native_p11f_wiring/step_400 \
  --tool_execution_budget 0 --no-difficulty_filter \
  --n 300 --seed 42 --gpus 0 --gpu_mem 0.2 --dump_traj \
  --out eval_p11f_recheck8192.json
# 随后用 analysis 的桶分布看 C/B/no-box 是否相对 §3.2 的 398/88/505 变差
```

### 4.1 重建在线宽表（0 代码，几十分钟 CPU）

```bash
P11F=rlab_new/native_p11f_wiring

# (a) 生命周期平均（对照用）
python -m rlab.passrate --record $P11F/record.jsonl \
  --difficulty_path rlab_out/difficulty_v3e1_train_online.jsonl \
  --difficulty_band 0.0 1.0 --min_k 8 \
  --merge_out rlab_out/difficulty_v3e1_train_online_wide_all.jsonl

# (b) 最近窗口（本轮要用这张）——先造 record 的尾部副本
tail -n 1600 $P11F/record.jsonl > /tmp/record_recent.jsonl
python -m rlab.passrate --record /tmp/record_recent.jsonl \
  --difficulty_path rlab_out/difficulty_v3e1_train_online.jsonl \
  --difficulty_band 0.0 1.0 --min_k 8 \
  --merge_out rlab_out/difficulty_v3e1_train_online_wide_recent.jsonl
```

**判读**：把两张表的三行"表过期诊断"和被在线覆盖的行数抄进本轮记录，并打印两张表的
`k=19` 刻度直方图——**它们之间的差就是"这轮训练把池子刻度推了多少"**。
若两张表差异很大，说明用生命周期平均会系统性低估当前策略，必须用 (b)。

> ⚠ `--min_k 8` 不是默认 16：一个 run 里每题约 8~19 条在线样本，用 16 会把绝大多数题排除在回填外
> （p11d §3.0 的同一理由）。**在线没覆盖到的题保留原表值**，所以这一步只会更准。

### 4.2 训练（纯配置改动）

`--out_dir` 换新目录（防同签名覆盖 `step_N`，p11 踩过两次）；**其余全部沿用
[p11d §3.1](p11d-run-config.md) 的定版命令**，只替换下面两行：

```bash
  --difficulty_path rlab_out/difficulty_v3e1_train_online_wide_recent.jsonl \
  --difficulty_band 0.1 0.8 \
  --out_dir rlab_new/native_p11g_poolmath
```

启动后**第一件事**是核对这两个自证读数（都在既有日志里）：

1. `[rollout] 难度过滤 band=(0.1,0.8): N -> K 题（全错 … / 全对 … / 区间外 …）`
   —— `K` 应明显小于 p11f 的池子；`全对`（`p_one`）应为 0；
2. `out_dir/difficulty_filter.json` 与日志一致。

### 4.3 权威判定（采样档，与 p11f 同批）

```bash
python -m rlab.eval --algo retool_math \
  --base_path=./rlab_out/sft_budget_v3/epoch1 \
  --models p11f_s400=./rlab_new/native_p11f_wiring/step_400 \
           p11g_s400=./rlab_new/native_p11g_poolmath/step_400 \
  --val_n 8 --tool_execution_budget 0 --no-difficulty_filter \
  --n 300 --seed 42 --gpus 0,1 --per_gpu 1 --gpu_mem 0.2 \
  --out eval_p11g_avg8.json

python -m rlab.analysis \
  --eval-json eval_p11g_avg8.json --pair-json eval_p11g_avg8.json \
  --pair-a p11g_s400 --pair-b p11f_s400
```

- **两臂同批**是硬要求（`gpu_mem` 0.20 vs 0.78 同权重同题差过 +7.0pp）。
- 判据按 §2.1：Δ≥+2pp 且 **z 检验 p<0.05**（采样档自动分派
  [paired_test_auto](<rlab/analysis.py#L141-L156>)；**不要**再看 McNemar）。
- 同时跑一次**该文件的 per-item 直方图**（p11f-diagnosis §9.5 的命令），
  看 p=0 的题数是否下降 —— 那是"边界池是否把难题推上去"的直接读数。

### 4.4 一次评测回答两个问题（可选，零额外成本）

同一条命令里把 ARCH 系臂换成 `--base_path` 起点，可顺带得到"池子改动 vs SFT 起点"的
配对读数；但**主判据只有 §2.1 的 p11g vs p11f**，别的都是诊断。

## 6. 明确不做（第二变量清单，防下一轮重复提议）

| 不做 | 原因 |
|---|---|
| 改 `num_pre_Q` 8→16 | §9.5 实算：inert 组 64.3%→59.1%、无梯度错答质量 62 里只捞回 2。**不是大杠杆** |
| 开 `--q_blacklist_ttl` | 属"题回流"机制，与池子组成是两个变量。本轮保持 `0`（逐位可比），留给下一轮 |
| 改 GAS / lr / 奖励 / 通告与执行预算 | 单变量纪律；且 `tool_call_cost` 的量级按真实轮长只有 ~0.035（§9.5 已修正） |
| 上 p11e 全对组效率训练 | 会改变上传组人群构成，与本轮归属冲突 |
| 用贪心档下结论 | 功效不够（b+c=54 只能给 p=0.34），已被 §9.2 证伪一次 |
| 让评测也跟着过滤 | `--no-difficulty_filter` 必须保持；课程决定"学什么"，评测口径决定"跟谁比" |

## 8. 未做清单（如实声明）

- 本方案**未实现、未上机**；上面所有 p11g 数字都是**预期**，不是读数。
- §1 的"36% → 92%"用的是 **2026-10 的 `k=8` 探针直方图**做量级估算；
  真实值要等 §4.1 用**在线率**重算（两张表对照）。
- `passrate` 是**跨权重版本的生命周期平均**，即使取最近窗口，也仍是"过去 N 个 attempt
  的平均策略"下测的，不等于启动时刻的当前策略——这是本方案最大的残留测量误差。
- hard 桶的 27.5% 错答质量在阶段 1 **仍然零梯度**（只是不再占主池算力）。
- 修复 `e166120` 的效果**尚未在真机验证**（需要重训后的 ckpt）。
- 训练 seed 只跑 42；要把它升格为"配方级结论"，需要第二个训练 seed（doc15 §6 建议 42/43）。
